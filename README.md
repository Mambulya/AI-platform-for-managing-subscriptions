# AI platform for managing personal subscriptions and regular payments
MVP for Sber internship 

AI-платформа для управления личными финансами в виде подписок на сервисы. Цель проекта — избавить пользователя от рутины ручных подсчетов в Excel и калькуляторе, предоставив интеллектуального агента, способного анализировать расходы на подписки и регулярные платежи на естественном языке.

# 1 Пользовательский сценарий
Пользователь задает вопрос в свободной форме (например, «Какая категория обходится мне дороже всего?»).
- ReAct-агент разбивает вопрос на шаги: получить список обязательств, сгруппировать по категориям, конвертировать валюты через внешний API (frankfurter.app), сравнить суммы.
- Агент прозрачно логирует свои рассуждения (Thought / Action / Observation), что позволяет отлаживать и доверять его ответам.
- Если данных недостаточно или произошла ошибка API курсов валют, агент честно сообщает об этом, а не выдумывает факты (галлюцинации).
- unit-тесты для обоих инструментов — минимум 3 теста.


# 2 Улучшения и доработки

## Использование вадидного API для конвертации валют
Не смотря на то, что в ТЗ был указан [frankfurter.app](https://api.frankfurter.app/latest?from=USD&to=RUB), данный сервис не поддерживает отныне Российский рубль. Валюта рассматривается в рамках задачи критической, поэтому было принято решение реализовать инструмент convert_currency() через аналогичный сервис, [v6.exchangerate-api.com](https://v6.exchangerate-api.com/v6/YOUR-API-KEY/latest/{RUB}). Рассмотренная альтернатива осуществляет поддержку RUB, что позволило уйти от существенных ограничений.

## Callback Handler для логирования ReAct-трейса 
Был реализован класс логирования, наследованный от langchain_core.callbacks.BaseCallbackHandler для отслеживания ReAct-трейса. Особенно для стадий Action и Observation. Однако есть _ограничение_ с Thought, так как в современных моделях ограничено отслеживание блоков рассуждений.

## Комплексный выход из диалога
Для поддержки окончания программы были реализованы 2 подхода: использование ключивых слов (exit, stop, стоп и др) и предоставление возможности модели самой поределять выходную точку из чата на основе слов пользователя. Первый подход быстрый, не перенагружает систему (рассматривается первым), но ипользование фиксированных лексических единиц весьма ограничено. Поэтому был реализован дополняющий подход за счёт решения модели. В контексте предложения LLM-модель при явном желании пользователя остановить диалог способна прекратить цикл за счёт интеграции дополнительного интсрумента finish_chat(). 


# 3 Выбор модели
Изначальный выбор модели был сфокусирван на GigaChat, так как отечественная модель гарантирует стабильный и безопасный доступ, что особенно актуально в production-задачах. В целях MVP проекта была интегрирвана модель GigaChat Lite, однако, даже при многих доработках системного промпта, модель галлюционирвала, выдавала неверные рассуждения (не оценивала все стоимости подписок) и выходила в вечный цикл в попытке использования инструмента finish_chat, который концентрировался на понимание окончания диалога со стороны пользователя. Возможно, использование версии мощнее устранило проблему. Однако было веское ограничение в токенах относительно тестирования.
Вследствие чего были рассмотрены другие LLM-модели на основании имеющиеся ограничений в рамках тестового проекта. Учитывались бесплатное пользование, количество доступных токенов, tool usage и загруженность относительно 1 суток. В итоге были рассмотрены следующие модели [источник](https://openrouter.ai):

|             | Free Access | Tool Usage  | Context length | Перегруженность | Latency |
| ----------- | ----------- | ----------- | -------------- | --------------- | ------- |
| GigaChat Lite| +           | +           |     131 K      |       :)        |  3 s    |
| ChatGPT-oss-20b    | +      |    +    |     131 K         |       :(        |   2.97 s |
| Gemma 4 31b|     +      |      +       |  262 K         |       :(        |  0.85 s | 
| Hy 3       |     +       |     +        | 262 K          |       :)        |  3.19 s | 
| Llama 3.3 70B |    +         |     +        |    131 K   |        :(         |  0.58 s    |

На основе полученных сравнений было решено попробовать использовать Hy3, так как модель предоставляла постоянную доступность вместе с подобающим пониманием конеткста, что было критически важно для MVP проекта.
Однако есть _ограничения_: работа через ограниченный доступ с российского адреса (в нынечшних реалях), случаи не способности обработки некоторых Unicode-символов, что решается через перезапрос. Например, "самая дорогая подписка в KZT?" -> "самая дорогая подписка? kzt" (UnicodeEncodeError может возникать из-за передачи русских символов (2 байта) в ASCII формат (1 байт). Подобное исключение отлавливается через except, не прерывая основную работу).

# 4 Запуск
Запуск основного модуля с агентом и тестовых модлей происходит за счёт Docker-контейнеризации. Чтобы протестировать приложение, пожалуйста, запустите Docker движок и композицию контейнеров, описанную в `Dockerfile` и `docker-compose.yml`.

Запуск unit-тестирования через pytest:
```console $
docker-compose run --rm tests
```

Запуск отдельных тестов инструментов:
```console $
docker-compose run --rm test_obligations_tool
```
```console $
docker-compose run --rm test_currency_tool
```

Запуск основного модуля для взаимодействия с агентом:
```console $
docker-compose run --rm agent
```
